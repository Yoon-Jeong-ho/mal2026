## Why this is a bounded repair

The v1 GPU0 actual Midm/all-five update completed its first rollout but all
four native-Transformers continuations failed the exact parser.  Qwen was not
called (`parse_valid=0`, `judge_calls=0`), so reducing the 1,920 train groups,
altering rewards, or changing judge prompts would not diagnose or repair the
failure.  The configured vLLM structured-output preflight instead passed 16 of
16 strict parses for the identical SFT adapter, four score-blind train prompts,
four completions each, temperature 0.7, top-p 0.95, and the same 512-token/
192-character bounds.

The new `configs/rlaif_grpo_prompt_ensemble.v2.json` is deliberately separate
from v1 so the negative result remains bound to its original digest.  It adds
no data, label, score, prompt-form, or optimizer change.

The first v2 server-only attempt (`20260722-006`) reached GPU0 health but the
local vLLM server returned HTTP 404 for its dynamic LoRA endpoint before any
restricted rollout or trainer process started.  Local vLLM source inspection
showed that this endpoint is intentionally disabled unless
`VLLM_ALLOW_RUNTIME_LORA_UPDATING=1`; the fresh next lineage sets only that
documented local server flag.  This is a launcher capability repair, not a
scientific result or a retry of an observed reward/validation outcome.

The next GPU0 actual attempt (`20260722-009`) passed the Qwen GPU0 schema
health gate, the dynamic-LoRA/structured-JSON policy-server gate, and then
completed one constrained policy rollout (four source rows, 16 sampled
continuations) before entering reward scoring.  It failed before one Qwen
judge call because the experimental TRL custom-rollout interface receives
rows that its `RepeatSampler` has *already* repeated once per generation.  The
first implementation requested four more choices for every repeated row and
returned 16 completion rows against four unchanged source metadata rows.  The
strict reward-column alignment check stopped the run at `global_step=0`;
the aggregate failure record reports `parse_valid=0`, `judge_calls=0`, and no
policy update.  No generated text was retained.  The bounded repair coalesces
each adjacent four-row repeat group into one local vLLM `n=4` request and
returns exactly four completions, preserving the declared four samples and
all scientific settings while removing the row-multiplication defect.  The
new GPU-free contract test asserts this exact output-cardinality invariant.

## Runtime topology

For a full v2 update, all authorized GPUs have a single fixed role:

| GPUs | Role |
|---|---|
| 0 | Midm/A.X/Phi vLLM policy rollout server, TP=1, dynamic LoRA, JSON-schema constrained |
| 1, 2 | float32 policy/ref GRPO DDP ranks |
| 3 | Qwen3.6 FP8 reward vLLM server, DP=1 |

The previous two-replica Qwen topology cannot coexist with a distinct policy
vLLM process and two policy ranks on only GPUs 0--3.  This is a throughput
partition change, not a change in the Qwen model, request, sampling seed, or
reward estimator; its single replica still batches the complete 64-completion
rollout (320 all-five or 64 random-one requests) and has a 192-sequence limit.
GPU0 must dynamically load the rank-zero current LoRA adapter before every
four-update rollout batch.  The trainer writes that ephemeral adapter only
under its ignored output root, waits for a local successful reload endpoint,
and then releases the prior ephemeral snapshot.  No raw prompt/completion is
stored by the synchronization mechanism.

For speed without changing either arm, the runner keeps the policy and reward
servers alive while it trains the paired `all5` and `random1` continuations of
one source adapter/task.  Each arm's first synchronization overwrites the
dynamic LoRA with its same frozen SFT starting adapter; no arm inherits the
other arm's learned weights.  This removes an otherwise redundant Qwen and
policy-server reload between paired arms.

## v2 hard gates before a full arm

1. vLLM server health and a synthetic dynamic-LoRA + strict-JSON request pass
   on GPU0.
2. A Midm bundled all-five and random-one actual one-update gate each have at
   least 98% exact policy parse validity, zero Qwen transport/schema failures,
   nonzero reward variance below the existing 80% zero-variance limit, a
   frozen reference hash, and no writing/candidate score access.
3. Only then run the two 480-update Midm arms and the unchanged DP=4 frozen-v6
   validation generation/judge comparison.  A score decrease is a preserved
   null result, not a tuning trigger; the other adapters still run under the
   same v2 recipe after Midm completes.

The v2 code and config are reproducibility inputs only.  Dynamic snapshots,
server logs, adapters, judge observations, generations, and reports remain in
ignored roots.

## Full Midm/all-five stop: synchronous decode tail

The first full Midm/all-five arm did **not** reach its declared completion
gate.  It completed one 64-continuation rollout and four optimizer updates:
strict policy parsing was 64/64, the score-blind Qwen reward made 320 calls,
the mapped reward mean/sd was 0.2885/0.4018, and the within-group zero-sd
fraction was zero.  These are runtime mechanics evidence only, not a model
comparison or a post-RL result.

The next 64-continuation rollout exposed a vLLM latency tail.  It began with
64 active sequences and drained to a few sequences; the final decode rate fell
to roughly 0.1--0.4 tokens/s while the GPU had little useful work.  The client
600-second request limit cancelled and deterministically reissued the same
four-output request twice.  vLLM aggregate metrics at the stop recorded 128
completed choices with `finish_reason=stop`, zero completed length-capped
choices, and four still-active tail choices.  Thus this was not a JSON/parser
failure, Qwen reward failure, or low-reward result, and reducing the number of
training essays would not remove the per-rollout tail.

The run was stopped after four completed optimizer updates rather than spend a
third identical timeout cycle.  The ignored aggregate-only stop record is
`outputs/rlaif-grpo-prompt-ensemble-v2/20260722-010/aggregate/midm2_bundle_all5_full_operator_stop.json`.
No adapter from this interrupted arm is eligible for evaluation or comparison;
no raw prompt, completion, essay, score, or judge response was retained.
